# Дизайн Агентской Системы (T-Lab 2026)

Этот документ описывает ролевую модель и протокол взаимодействия агентов для выполнения исследовательского проекта.

## 1. Роли агентов

В проекте участвуют четыре специализированных агента:

1. **Планировщик (Planner)**
   - **Обязанности:** Держит целиком `PLAN.md`. Превращает Go/No-Go критерии каждой стадии в конкретный список подзадач для исполнителей. Обрабатывает эскалации (меняет ТЗ, разбивает задачи). Не пишет код.
2. **Кодер (Coder)**
   - **Обязанности:** Пишет инженерный код (PyTorch, логика среды, модули памяти, пайплайны запуска). Работает по ТЗ Планировщика.
   - **Масштабирование:** На стадиях с независимыми файлами (например, реализация разных методов памяти на Stage 3) запускаются несколько параллельных инстансов Кодера.
3. **Аналитик (Analyst)**
   - **Обязанности:** Работает с данными. Выполняет прогоны по готовым конфигам, читает CSV, строит графики (`matplotlib`), считает bootstrap CI, проверяет монотонность и статистическую значимость. Пишет числовые и аналитические разделы отчета. Не трогает архитектуру нейросетей.
4. **Верификатор (Verifier)**
   - **Обязанности:** После каждой стадии (не подзадачи) сверяет результат с Go/No-Go гейтом из `PLAN.md`. Запускает реальные команды для проверки. Вердикт Go/No-Go является обязательным для перехода дальше.

## 2. Разделение зон ответственности (Кодер vs Аналитик)

| Stage | Зона ответственности Кодера | Зона ответственности Аналитика |
|---|---|---|
| **1-3** | `env/`, `agent/`, `memory/` — полная реализация | Не участвует |
| **4 (H1)** | Подготовка конфигов + написание `experiments/run.py` (движок) | Запуск грида, `analysis/make_plots.py`, проверка монотонности (learning curve, trap-accuracy) |
| **5 (H2)** | Написание конфига дрейфа | Запуск, графики `post-return` vs `post-new`, интерпретация результатов |
| **6 (Анализ)** | Опциональные задачи (ablation, LoRA) | Bootstrap CI, раздел "альтернативные объяснения" |
| **7 (Отчёт)** | Финальный `README.md`, команда воспроизведения | Написание числовых/аналитических разделов в `report/report.md` |

## 3. Протокол взаимодействия

**Стандартный поток:**
Планировщик читает `PLAN.md` → пишет ТЗ → Кодер/Аналитик реализуют → Верификатор проверяет против гейта → переход к следующей стадии (при Go).

## 4. Механизм эскалации (защита от зацикливания)

Для предотвращения бесконечных циклов вводится счетчик неудачных Go/No-Go циклов на **одной и той же подзадаче**:

1. **Попытки 1-3:** Верификатор даёт No-Go с конкретной причиной → та же роль (Кодер/Аналитик) исправляет код и присылает заново.
2. **Эскалация 1 уровня (после 3 неудач):** Возврат к Планировщику. Планировщик **не** просто просит "исправить", а кардинально меняет ТЗ (разбивает подзадачу мельче, меняет архитектурный подход, уточняет неоднозначность).
3. **Эскалация 2 уровня (еще 2 неудачи, итого 5 циклов):** Эскалация к Человеку (пользователю) — конкретным вопросом с вариантами (через `AskUserQuestion`), а не открытым "что делать?". Планировщик формулирует развилку: в чём именно расходятся попытки, какие варианты решения рассмотрены и почему не сработали.

Каждая эскалация логируется явно, чтобы обеспечить прозрачность процесса.

**Уточнение единицы счёта:** "подзадача" — это один файл/один самостоятельный кусок работы внутри стадии (например, в Stage 3 — файл `memory/decision_aware_mem.py`; в Stage 4 — файл `experiments/run.py`), а не вся стадия целиком. Иначе один трудный edge-case в одном файле мог бы откатить всю стадию к Планировщику, хотя проблема локальна.

**Отдельно от эскалации по неудаче — эскалация по несоответствию плана реальности.** Если причина No-Go не в качестве кода, а в том, что предпосылка `PLAN.md` оказалась неверна (пример из Stage 0: `uv` подхватил незапланированную версию Python; из PLAN.md Stage 2 — калибровка может показать, что грид не помещается в 3–4 часа) — это **не** идёт через счётчик 3→5. Планировщик сразу помечает это как **архитектурное изменение**, вносит правку в сам `PLAN.md` (с явной пометкой, что изменилось и почему), и только потом переформулирует ТЗ. Подменять предпосылки плана молча, под видом "просто ещё одна попытка", нельзя.

## 5. Контекст-пакет для агента (что именно передаётся при диспетчеризации)

Каждый вызов Кодера/Аналитика/Верификатора — это новый агент без памяти о разговоре. Чтобы не терять инварианты между стадиями (пример реальной ошибки, которую это предотвращает: черновик `start.md` дал Decision-Aware памяти другой энкодер, чем Semantic-RAG, и confound всплыл только на ревью), в ТЗ каждый раз явно кладётся:

1. **Роль** — одна строка ("Ты — Кодер, пишешь только `memory/decision_aware_mem.py`, не трогаешь остальные файлы `memory/`").
2. **Точная выдержка из `PLAN.md`** для этой стадии — не весь файл, а раздел "Этапы выполнения" (нужная строка) + любые связанные инварианты из раздела "Итоговый рисёрч-дизайн" (например, требование общего энкодера у Semantic-RAG/Decision-Aware — это конкретно тот факт, который нельзя не передать).
3. **Явные границы** — какие файлы можно создавать/менять, какие нельзя трогать (особенно важно для параллельных Кодеров на Stage 3).
4. **Гейт** — дословно Go/No-Go критерий, который будет проверять Верификатор, и команды, которыми он это сделает (Кодер должен целиться в них сам, не только Верификатор).
5. **Формат отчёта** — что агент обязан вернуть (не "готово", а конкретный вывод команд, как это уже требуется от Верификатора).

Без пункта 2 и 3 система вырождается в "перескажи PLAN.md своими словами" — источник как раз тех confound-ошибок, которые мы уже один раз ловили на ревью Stage 0/дизайна среды.

## 6. Права и инструменты по ролям

| Роль | Инструменты | Не делает |
|---|---|---|
| Планировщик | Read, Grep/Glob, Agent (диспетчеризация), AskUserQuestion (эскалация 2 уровня) | Write/Edit кода, `git commit` |
| Кодер | Read, Write, Edit, Bash (в пределах своих файлов) | `git commit`, правки чужих файлов из ТЗ |
| Аналитик | Read, Bash (python/pandas/matplotlib), Write (только `analysis/`, `report/`) | Не трогает `env/`, `agent/`, `memory/` |
| Верификатор | Read, Bash (только для запуска проверочных команд) | Не пишет код; правки — только собственный вердикт |

**Честная оговорка:** в текущем харнессе (Claude Code, Agent tool) это разграничение — соглашение в тексте ТЗ, а не программный sandboxing: диспетчеризуемые `general-purpose` агенты технически получают одинаковый набор инструментов независимо от названной роли. Дисциплина обеспечивается формулировкой ТЗ и тем, что Верификатор реально проверяет `git status`/`git diff` на предмет вылезших за границы правок (как уже было на Stage 0 — явная проверка "ничего из superpowers не утекло") — а не тем, что роль физически не может выйти за рамки.

## 7. Git-дисциплина

- `git commit` делает **только оркестратор** (я, в роли, объединяющей функцию Планировщика в этой сессии) — и только после вердикта Go от Верификатора. Кодер/Аналитик готовят файлы, но не коммитят сами.
- Коммит — один на стадию (или на логически цельное исправление внутри стадии, как `Stage 0 fix: pin Python to 3.11` было отдельным коммитом от `Stage 0: repo scaffold`), а не один на файл/подзадачу.
- На Stage 3 (5 параллельных Кодеров в `memory/`) — правило "один Кодер = один файл, не трогает соседние" из Раздела 5 снимает риск конфликтующих правок; общий `memory/base.py` пишется одним Кодером первым, до параллельного запуска остальных.
- Если Верификатор дал No-Go после того, как файлы уже готовы — не коммитим частично. Коммит только на итоговый Go по всей стадии.

## 8. Когда НЕ разворачивать полный протокол (моя оценка)

Для строго последовательных инженерных стадий без развилок и без параллелизма — сейчас это **Stage 1 и Stage 2** — полная диспетчеризация всех ролей избыточна: там нет ни параллельных файлов, ни спорной интерпретации результатов, только последовательная реализация по уже детализированному ТЗ. Дороже по токенам и времени, чем оправдано.

Моя рекомендация: полноценно разворачивать все 4 роли отдельными dispatch там, где есть хотя бы одно из:
- **параллелизм** (Stage 3 — 5 методов памяти; частично Stage 6 — ablation можно вести параллельно с bootstrap CI);
- **независимая проверка обязательна и уже стандартна** — Верификатор всегда отдельный dispatch, на любой стадии, без исключений (единственная роль, для которой экономия неуместна: смысл именно в том, что она не видела, как писался код);
- **интерпретация напрямую влияет на научный вывод** — Аналитик на Stage 4-6, потому что ошибка в графике/CI искажает вывод по H1/H2, а не просто ломает тесты.

На Stage 1 и 2 предлагаю: я как оркестратор напрямую выполняю функцию Кодера одним последовательным потоком (как уже делали на Stage 0), а Верификатора всё равно диспетчеризую отдельным вызовом — это единственная точка, где независимость нельзя заменить самопроверкой оркестратора (см. Раздел 9, "ложный Go").

## 9. Риски самой агентской системы (не проектной части, а процесса)

- **Потеря инварианта при передаче.** Агент, не видевший обоснования смежной стадии, может незаметно нарушить условие, которое казалось "очевидным" из контекста разговора, но не было явно продиктовано. Снимается Разделом 5 (контекст-пакет) — но это дисциплина, которую легко нарушить в спешке, стоит держать в голове как системный риск, а не разовое правило.
- **Стоимость координации.** Каждый dispatch — заново прочитанные файлы и токены на ориентацию в проекте; для мелких задач (см. Раздел 8) это может стоить дороже, чем прямое исполнение.
- **Race conditions при параллельных Кодерах**, если границы файлов из ТЗ нарушаются (например, Кодер решает "заодно поправить" общий `base.py`). Снимается явным перечислением запрещённых путей в каждом ТЗ и тем, что коммитит только оркестратор — конфликт будет виден в `git diff` до коммита, а не тихо перезапишет чужую работу.
- **Ложный Go.** Верификатор тоже может ошибиться, если поверит прошлому выводу вместо повторного запуска "с нуля" — именно так на Stage 0 был обнаружен пропущенный регресс на Python 3.14 (Верификатор запустил проверки заново, а не переиспользовал старый вывод). Это уже прописано как обязательное правило Верификатора (Раздел 1), но стоит явно называть системным риском: любое ослабление этого правила ради скорости — самое опасное место всей схемы, потому что ошибка становится незаметной именно в момент, который должен был её поймать.

## 10. Соответствие с установленными skills `superpowers`

Плагин `superpowers` сейчас установлен в сессии (доступен через `Skill` tool). Формально этот протокол — специализация под конкретный research-план уже существующих в нём паттернов, не что-то с нуля:
- **subagent-driven-development** — свежий субагент на задачу + ревью после каждой; наш протокол делает то же самое, но с привязкой к конкретным Go/No-Go гейтам из `PLAN.md`, которых generic-skill не знает.
- **dispatching-parallel-agents** — используется на Stage 3 (и частично 6) для независимых файлов/подзадач.
- **requesting-code-review / verification-before-completion** — роль Верификатора замещает оба: он и ревьюер, и требует реальных доказательств перед "готово".

Можно было бы вызывать эти generic-skills напрямую вместо кастомного протокола — но тогда пришлось бы каждый раз заново объяснять специфику проекта (гейты, инварианты, разделение Кодер/Аналитик по типу работы). Кастомный протокол в этом файле — не отказ от skills, а их конкретизация под этот проект; при желании реализацию отдельных стадий всё равно можно провести через `superpowers:subagent-driven-development`, просто держа в уме роли и гейты из этого документа.
